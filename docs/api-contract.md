## 一、通用约定

### 认证

除 `/healthz`、`/auth/register`、`/auth/login` 外，**所有接口都需要**：

```
Authorization: Bearer <access_token>
```

### 身份来源（重要）

**`user_id` 一律从 token 解析，任何接口都不接受前端传入 `user_id`。**

所有涉及资源的查询必须带归属条件：

```sql
WHERE id = :id AND user_id = :current_user_id
```

查不到时返回 **404**，不返回 403 —— 403 会泄露"该记录存在"，等于帮攻击者确认有效 ID。

### 统一错误格式

```json
{
  "detail": "人类可读的错误说明",
  "request_id": "ab12cd34"
}
```

`request_id` 用来在日志里定位那一次请求（由中间件注入，见 `app/main.py`）。

### 状态码约定

| 码 | 什么时候用 |
|---|---|
| 200 | 成功（查询、更新） |
| 201 | 成功创建资源 |
| 400 | 业务错误（如"PDF 里提取不到文字"） |
| 401 | 未登录 / token 无效或过期 |
| 404 | 资源不存在，**或不属于当前用户** |
| 422 | 参数格式错（FastAPI/Pydantic 自动返回） |
| 429 | 触发限流 |
| 500 | 服务端未预期异常 |

## 三、三条关键设计决策（面试要能讲）

### D1 · 提交回答用 `POST`，不用 `GET`

**理由**：
1. 有副作用（保存回答、推进状态、消耗 token）
2. `GET` 的语义约定是"只读、可重复、可缓存" —— 浏览器刷新、预加载器都会自动重发 `GET`，如果它会改数据，刷新一次就多提交一次
3. `GET` 理论上不带请求体，回答正文只能放 body
4. URL 有长度限制（约 2000 字符，中文编码后膨胀 9 倍）

**为什么不拆成"POST 保存回答" + "GET 取下一题"**：可以，但多一次往返，且产生"保存成功但取题失败"的中间态需要额外处理。一个请求能原子完成的事，不拆。

### D2 · 分析用「触发 + 查询」两个接口，不用一个同步接口

**理由**：一次分析要调 LLM，15~25 秒。同步接口会出三种事故：

| 情况 | 后果 |
|---|---|
| 用户刷新/关页面 | 后端还在算，钱照扣，结果没人收 |
| 网络抖动 | 前端没收到，后端算完白算 |
| 想重试 | 重试 = 再算一遍 = 双倍成本 |

**模式名**：异步任务 + 轮询（polling）。
**阶段 C 的升级**：把轮询换成 SSE 推送，解决"空转"和"延迟"两个问题。
**刻意不做的**：不引入 Celery + Redis 任务队列 —— 这个规模用 `BackgroundTasks` 就够，能不上分布式就不上。

### D3 · `user_id` 只从 token 解，且跨用户访问返回 404

**理由**：前端传来的一切都可以被改（打开开发者工具就能改请求体）。从请求体读 `user_id` = 水平越权漏洞。

**关键细节**：URL 里的 `{id}` 也必须做归属校验，查不到返回 **404 而非 403**。
403 等于告诉攻击者"这条记录存在，只是不属于你"，404 什么都不泄露。

## 四、实现顺序（阶段 B）

```
B1 用户系统      → 接口 1/2/3
B2 简历解析      → 接口 4/5/6
B3 匹配度分析    → 接口 7/8（含异步任务）
B4 会话管理      → 接口 11 的存储部分
B5 RAG 知识库    → 接口 13/14
B6 模拟面试      → 接口 9/10/11/12
```

**每个阶段做完，对应的接口就能用 curl 独立验证** —— 这是"契约先行"最实际的收益。
